      Proposal format and review limits
      
    
        Use the following JSON as the description of a Sputnik Vote. For a native NEAR Transfer, use
        the Transfer JSON as its description. Replace the example reference with
        network/DAO/approval-ID. The recipient and amount are read from the actual Transfer action.
      
    
      
    
      
    
        DAO records are read together at one finalized block. Version 3 adds named delegation and
        checks credentials at the registry block chosen in the original mandate. Use a real
        finalized block hash from before opening the round; older snapshots may need archival RPC
        access. A member can delegate to one enrolled representative for this payout. Only a
        representative with a valid direct ballot can represent others. Version 2 requires a DAO
        approval plus a separate ballot round. Each enrolled account casts a ballot by submitting a
        signaling Vote proposal. The proposer identifies the voter. The first valid ballot per
        eligible credential counts. Nine credits buy support for payment or keeping funds, at the
        square of each allocation. Quorum and a strict pay majority are required. Version 2
        credentials are checked at the review block through the network’s I-Am-Human registry.
        Version 1 shows the original DAO approval only. A match covers the listed fields only.
        Version 3 flags an earlier pending or approved transfer proposal that cites the same
        mandate. Treasury members control execution. Actual settlement must be checked separately.
        Trezu’s Requestor and Finance roles control submission and approval.
